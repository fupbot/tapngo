# TapNGo — Development Log

This document provides a chronologically structured log of the steps, trade-offs, and decisions taken during the design and development of the **TapNGo** self-service kiosk system.

---

## High-Level Step-by-Step Log

* **Step 1: Requirements Gathering & Domain Exploration**
  * Analyzed quick-service snack bar kiosk requirements: standalone touch-screen operation, unattended edge cases, high throughput, and lack of cashier support.
  * Identified key domain risks: abandoned carts, double-tap race conditions, inventory exhaustion concurrency, and unexpected network/payment failures.

* **Step 2: Architectural Specification & Stack Selection**
  * Selected Python 3.12 with **FastAPI** for backend high performance, asynchronous request handling, and clean OpenAPI auto-generation.
  * Selected **SQLite with SQLAlchemy 2.0** with WAL (Write-Ahead Logging) mode and busy timeout handling for robust transactional persistence without extra infrastructure overhead.
  * Chosen **React + TypeScript + Vite** for lightweight, touch-optimized frontend UI state management and target sizing.
  * Defined **Docker Compose** containerization with **NGINX** reverse proxy for unified client/API routing.

* **Step 3: Database Schema & Core Models Definition**
  * Designed SQL schema for `products`, `orders`, `order_items`, and `payment_transactions`.
  * Configured order status lifecycle transitions: `PENDING` $\rightarrow$ `PAID` $\rightarrow$ `PREPARING` $\rightarrow$ `COMPLETED` / `CANCELLED`.
  * Implemented database dynamic seeding script (`seed.py`) to initialize default product catalog items with starting stock levels.

* **Step 4: Backend API & Service Layer Implementation**
  * Implemented RESTful API endpoints for catalog browsing (`/api/v1/products`), order creation (`/api/v1/orders`), and payment execution (`/api/v1/payments`).
  * Integrated atomic transaction handling and dynamic inventory decrement checks during checkout.
  * Added concurrency protection using payment timestamp ordering to resolve simultaneous stock claims cleanly.

* **Step 5: Payment Service Abstraction & Admin Failure Controls**
  * Created pluggable `PaymentService` strategy abstraction supporting Credit Card (tap/chip), Mobile Pay (Apple/Google Pay), and Store Card.
  * Implemented lightweight authentication separating regular kiosk clients (`kiosk1`, `kiosk2`, `kiosk3`) from `admin` users.
  * Built an admin failure injection mechanism enabling forced payment declines, timeouts, or backend error simulation for UI resilience verification.

* **Step 6: Touch-First Kiosk UI & Ergonomics**
  * Developed React frontend with high-contrast UI components, touch targets ($>48\text{px}$), and single-touch interaction constraints.
  * Implemented automatic **15-second idle detection** triggering a 15-second modal countdown prompt ("Are you there?") before resetting to the home screen.
  * Added a **3-second order confirmation banner** display before returning to the initial "ORDER HERE" state for subsequent customers.

* **Step 7: Containerization & Reverse Proxy Setup**
  * Created multi-stage `Dockerfile` for backend Uvicorn application and frontend Vite React build.
  * Configured NGINX reverse proxy to serve frontend SPA routes while routing `/api/*` to FastAPI application seamlessly.
  * Authored `docker-compose.yml` for single-command environment bootstrapping (`docker compose up --build`).

* **Step 8: Testing & Verification (original plan — see Step 18 for what was actually built)**
  * At this point in the project, testing was still a forward-looking plan, not yet implemented — matching the earlier decision to write tests last rather than test-first. This entry described the intended scope before any test file existed.
  * **Correction:** the original wording here claimed frontend tests would cover "timer behavior," "single-tap constraints," and "order confirmation UI cycles." The suite actually written in Step 18 deliberately does not cover these — they're UI/integration surfaces (idle countdown, multi-touch guard, the 3-second auto-return) that would need component rendering, timers, and DOM event simulation to test meaningfully, which is disproportionate to the "simple, core functionality, not maximum coverage" brief the suite was actually built to. Left this note rather than quietly rewriting history, since the original claim was inaccurate to what got built.

* **Step 9: Pre-Implementation Review Pass**
  * Before writing code, reviewed the initial spec against the goal of a lean, few-days build rather than maximal scope. Concrete changes made as a result:
    * **Concurrency:** Replaced the "resolve by comparing payment timestamps across requests" framing with a single atomic `UPDATE ... WHERE stock >= 1` decrement. SQLite serializes writers regardless, so a timestamp-comparison mechanism added complexity without changing the customer-facing outcome — whichever request's atomic decrement commits first wins; the other gets a 409.
    * **Order lifecycle:** Nothing in scope ever drives `PREPARING` → `COMPLETED` (no kitchen/staff app). Rather than leave that dangling, it's auto-simulated by a short server-side timer after `PAID`.
    * **Admin access:** Specified how an admin actually reaches the debug/failure-injection panel without the customer flow ever showing a login prompt — a discreet long-press gesture on a small header element, kept out of the normal tap path.
    * **Failure handling scope:** Extended beyond admin-forced failures to cover real unprompted failures (dropped network, timeout, unexpected 500) with one consistent client-side error/retry pattern.
    * **Cut branded physical collateral** (cup/wrapper mockups) — graphic design effort that doesn't demonstrate engineering judgment; kept the color palette and wordmark only.
    * **Folded the requirements-elicitation Q&A into this log and the ADR** rather than keeping the raw transcript as a separate file, so the repo reads as project documentation rather than an interview artifact.

* **Step 10: Backend Implementation**
  * Created a Python 3.12 venv at `backend/venv` and pinned dependencies (`fastapi`, `uvicorn`, `sqlalchemy>=2.0`, `pydantic`, `pydantic-settings`) to `requirements.txt`.
  * Built the SQLAlchemy 2.0 models (`User`, `Product`, `Order`, `OrderItem`, `PaymentTransaction`) and wired SQLite WAL mode + busy timeout via a `PRAGMA`-setting `connect` event listener.
  * Implemented `POST /api/v1/orders` (creates a `PENDING` order from a cart), `GET /api/v1/orders/{id}` (status polling), and `POST /api/v1/orders/{id}/pay` — the core endpoint, which:
    * runs the pluggable `PaymentProcessor` strategy (credit card / Apple Pay / Google Pay / store card, all mock),
    * on success, atomically decrements stock per item (`UPDATE ... WHERE stock >= quantity`) inside the order's transaction, rolling the whole order back to `CANCELLED` with a 409 if any item sold out, per the simplified concurrency approach from Step 9,
    * on an admin-forced `debug_failure_mode`, returns a 402 (decline), 504 (timeout), or 500 (server error) so the frontend has real failure responses to build against.
  * Added `GET /api/v1/products` and `POST /api/v1/auth/login` (plaintext password check against the `users` table, no hashing/JWT — intentional, per spec).
  * Gated `debug_failure_mode` server-side on an `X-Role: admin` header the client re-sends after login — trivial by design, documented in `app/deps.py` as not real security.
  * Wrote an idempotent `seed.py` (runs on every app startup) seeding 4 users (`admin`, `kiosk1-3`) and a 14-item snack bar menu across 4 categories, with one item (`Nachos`) deliberately seeded at 0 stock to exercise the sold-out UI state immediately.
  * Order lifecycle (`PAID` → `PREPARING` → `COMPLETED`) runs via FastAPI `BackgroundTasks` on a worker thread (not `asyncio.create_task`, which has no running loop to attach to from a sync endpoint dispatched to FastAPI's threadpool).
  * Smoke-tested every path manually with `uvicorn` + `curl`: catalog fetch, order creation, successful payment + stock decrement, lifecycle auto-advance, sold-out 409, non-admin 403 on forced failure, admin-forced decline/timeout/server-error (402/504/500).

* **Step 11: Frontend Shell**
  * Scaffolded Vite + React + TypeScript, added Tailwind v4 (via `@tailwindcss/vite`) and React Router. Set up a `@/` path alias and a dev-server proxy (`/api` -> `localhost:8000`) mirroring the NGINX routing the Docker Compose setup will use.
  * Defined the "Kiosk Fresh" design tokens (teal/orange/white palette, Poppins display font) as Tailwind `@theme` variables in `index.css`; disabled pinch-zoom/double-tap-zoom at the document level.
  * Built the navigation shell: `Layout` (header, admin gesture target, idle-warning modal) wrapping routed pages — Landing, Menu, Payment, Confirmation — via React Router.
  * Implemented the three cross-cutting kiosk behaviors as dedicated hooks: `useIdleReset` (15s idle -> 15s "Are you there?" countdown -> clear cart + return to landing), `useSingleTouchGuard` (rejects multi-touch at the document level), `useLongPress` (the discreet admin-access gesture, no visible affordance).
  * Wired a typed API client (`lib/api.ts`) against the real backend — login, product fetch, order creation, and payment, including the 402-decline special case (a legitimate business outcome carrying a full response body, not a wire-level error).
  * Built out the actual pages against the live API: Menu (grouped by category, sold-out items disabled, running cart footer), Payment (order summary, 4 payment method tiles, admin-only failure-simulation radio panel, error/retry handling for declines/409/504/500), Confirmation (order number, 3s auto-return).
  * **Verification:** `tsc -b`, `vite build`, and `oxlint` all pass clean. Headless-browser verification wasn't available out of the box (missing shared libs, no root) — worked around it by downloading the required `.deb`s with `apt-get download` (no install) and pointing `LD_LIBRARY_PATH` at the extracted `.so` files, rather than skipping visual verification. Drove the app end-to-end with Playwright against the real backend: landing -> menu -> cart -> payment -> confirmation -> auto-return; admin long-press -> login -> forced decline; and a real 15s+15s idle-reset cycle. Zero console errors; screenshots confirmed the palette, layout, sold-out state, and all three edge-case flows render as designed.

* **Step 12: "Back to menu" / "Cancel order" on the payment screen**
  * Payment screen had no way out short of the browser back button. Added a `POST /api/v1/orders/{id}/cancel` endpoint (only valid from `PENDING`, so it can't cancel an already-paid or already-dead order) and two controls: "Back to menu" (keeps the cart, lets the customer adjust items) and "Cancel order" (clears the cart, returns to landing) — both mark the abandoned order `CANCELLED` server-side instead of leaving it dangling `PENDING` forever.
  * Verified with Playwright: cart survives "Back to menu," "Cancel order" clears it, and the backend correctly 409s on double-cancel or paying a cancelled order.
  * Along the way, learned the hard way not to `rm` the SQLite file while a server might already be pointed at it — deleted it out from under a running `--reload` backend mid-session and crashed it. Fixed by restarting; no data of consequence was lost (seed data + a few test orders), but it's a reminder to check `lsof`/`ps` before touching a live DB file, not just before destructive git operations.

* **Step 13: "Trailhead" visual identity**
  * Replaced the teal/orange "Kiosk Fresh" identity with a Pacific Northwest trailhead-café identity — forest green + clay/terracotta on warm cream, `Fraunces` + `Inter` typography instead of the bold rounded sans-serif, and Tailwind's warm `stone` scale instead of cool `slate` for borders/neutrals. Same logo mark, same buttons, same functionality — visual layer only.
  * Replaced emoji (14 per-product glyphs + 4 payment-method glyphs) with a small hand-drawn line-icon set (`components/icons.tsx`): cup/acorn/flame/dotted-circle for the four menu categories, card/tap/ticket for payment methods. Icons are applied per category rather than per product — color emoji is inherently a bright cartoon glyph on every platform regardless of which character is chosen, so the fix was to stop using emoji at all rather than pick "calmer" ones.
  * Removed the now-fully-unused `emoji` field end-to-end (`Product` model, `ProductOut` schema, seed data, frontend `Product` type) rather than leaving dead data behind.
  * Added one restrained nature touch — a thin single-line mountain-ridge motif at the base of the landing screen — instead of scattering decorative elements throughout.
  * Re-verified the whole flow visually with the same Playwright setup: landing -> menu -> cart -> payment -> confirmation, zero console errors, new palette/icons/typography confirmed via screenshots.

* **Step 14: Category picker screen + per-product icons**
  * Split the single scrolling menu page into two steps: a category picker (four big buttons — Drinks, Snacks, Hot Food, Desserts) between Landing and the item list, and the item list itself now shows one category at a time with a "← Categories" back button. Routing: `/menu` (picker) and `/menu/:category` (items), nested under the existing layout. Cart state lives in the shared session context regardless of route, so it survives switching categories.
  * Restored per-product icons (one per menu item, in the same hand-drawn line-icon style used for categories/payment methods) — a can, bottle, tall glass, and short tumbler for the four drinks; a chip, pretzel-loop, popcorn box, and pouch for snacks; a hot dog, nacho triangle, and pizza slice for hot food; a chocolate-bar grid, cookie, and ice cream cup for desserts (`components/icons.tsx`, mapped by product name in `lib/productIcons.ts`).
  * **Legibility problem found via screenshot, not assumption:** the first pass differentiated similar-looking drinks (sparkling water / iced tea / orange juice) only by tiny internal details — bubbles, an ice cube, a citrus wedge — inside an identical glass outline. At the ~32px size these actually render in a product card, those details were invisible; all three looked like the same empty glass. Fixed by giving each drink a genuinely different **outer silhouette** (bottle vs. tall tapered glass vs. short tumbler vs. can) and treating the internal details as a bonus accent, not the primary signal. Also caught and fixed an inverted arc sweep-flag on the pizza slice icon that made the crust curve inward instead of out (looked like the letter "A" until corrected).
  * Re-verified visually: zoomed crops of the rendered PNGs (not just eyeballing the full screenshot) to confirm each icon reads correctly at actual card size, cart persists across category switches, and the full order flow still works end-to-end.
  * **Found a real gitignore bug while checking status:** the root `.gitignore` (a generic Python template) had a bare `lib/` rule intended for Python packaging artifacts, but gitignore patterns without a leading slash match at any depth — so it was also silently matching `frontend/src/lib/`, excluding `api.ts` (and now `categories.ts`/`productIcons.ts`) from version control entirely since the frontend was first scaffolded. A fresh clone would have been missing the API client and failed to build. Removed the redundant `lib/`/`lib64/` lines (already covered by `backend/.gitignore`'s wholesale `venv/` exclusion) and confirmed the frontend's `lib/` directory is now tracked.

* **Step 15: Abuse-vector review + per-item quantity cap**
  * Talked through what a bad-faith kiosk user could actually do to this system: enumerate/pay/cancel other customers' orders by guessing IDs (no order ownership check — the real finding, fix pending), spoof `X-Role: admin` via a plain header to force failures on anyone's order, and — the one a live test surfaced directly — spam-tap a product with no client-side cap, hitting the backend's then-20-unit Pydantic ceiling and getting FastAPI's raw validation-error shape (a list of objects) back, which the frontend's `String(detail)` handling mangled into a literal "[object Object]" on screen.
  * Implemented the requested rule — cap each line item at `min(5, current stock)` — on both sides: `SessionContext.addToCart` now enforces it inside the state updater itself (not just a disabled button), specifically so a rapid-fire double-tap can't sneak an extra unit in before React re-renders the disabled state; `routers/orders.py` enforces the same cap server-side with a friendly message ("You can add up to 5 of Cola right now." / "Nachos is sold out.") rather than relying on Pydantic's field bound for the real business rule. The Pydantic bound itself was loosened to `le=99` — now purely a sanity ceiling against garbage payloads, not the actual limit.
  * Fixed the underlying bug regardless of the new cap: `lib/api.ts` now has a shared `extractErrorMessage` helper that handles both a plain string `detail` and FastAPI's list-of-error-object `detail`, so any future validation error (not just this one) renders as readable text instead of `[object Object]`.
  * Verified end-to-end: curl against the backend for qty=95 (blocked with a friendly 400), qty=200 (still hits the raw 422, confirming the frontend needed its own fix independent of the cap), and a sold-out item; then a Playwright script rapid-tapped Cola 20 times in the running UI and confirmed the cart stopped at 5 with a "Limit reached" label, zero console errors.
  * Order-ownership (IDOR) and the spoofable admin-role header are still open — next up.

* **Step 16: Fixed the order-ownership IDOR**
  * Added a random `access_token` (`secrets.token_urlsafe(16)`) to `Order`, generated at creation and returned once in the response. `GET /orders/{id}`, `POST /orders/{id}/pay`, and `POST /orders/{id}/cancel` now all require that token back via `X-Order-Token`, checked with `secrets.compare_digest`; a missing/wrong token gets the same `404` as a nonexistent order ID, so a guess can't even confirm the order exists. Threaded the token through the frontend (`PaymentPage` holds it in component state alongside the order ID, `lib/api.ts` sends it on every subsequent call).
  * Verified with curl: no token -> 422 (FastAPI's own missing-header validation), wrong token -> 404 on both `GET` and `pay`, correct token -> normal 200/201 responses. Then verified the real UI end-to-end (order -> pay -> confirmation, and separately order -> cancel) with zero console errors.
  * **Self-inflicted detour worth recording:** mid-verification, deleting `tapngo.db*` while the backend was running (again — see Step 12's note) produced a genuinely confusing intermittent `sqlite3.OperationalError: no such table: products` and a React "Cannot update a component while rendering a different component" warning that looked like real app bugs. Root cause: SQLAlchemy's connection pool opens new physical SQLite connections lazily across the threadpool FastAPI dispatches sync endpoints to; deleting the file mid-session let some already-open connections keep working (fine) while any *new* pooled connection created after the delete silently recreated an empty, schema-less file at the same path (also "fine" from SQLite's perspective — `sqlite3.connect()` just makes a new file). Some requests succeeded, some 500'd, depending on which connection happened to serve them — which is what produced the flaky, hard-to-explain test failures. This also **retracts** something said out loud earlier in this session: a single connection surviving a `rm` while a process holds it open is true and is *not* the risk; the real risk is concurrent connection-pool churn creating a fresh file at the same path. Fix was procedural, not code: always fully stop the server before deleting its DB file, never delete-then-restart in one breath.

* **Step 17: Closed two loose ends before writing tests**
  * **Wired up the previously-unused `kiosk1`/`kiosk2`/`kiosk3` accounts.** They were seeded from day one but nothing ever signed in as one — a sharp reviewer reading `seed.py` would reasonably ask what they're for. Clarified the actual intent (identifying *which physical terminal* placed an order, not a customer login — self-service kiosks don't authenticate the customer) and wired it minimally: `frontend/src/lib/kiosk.ts` reads `VITE_KIOSK_ID` (documented in a new `frontend/.env.example`, defaulting to `kiosk1` so a fresh clone still works with zero config), shows it as a small label next to the logo, and passes it as `kiosk_username` when creating an order. No login flow involved.
  * **Added `POST /orders/{id}/refund`.** Previously, cancellation only worked pre-payment (`/cancel` on a `PENDING` order) — "I paid and changed my mind" had no path at all, not even on the backend. The new endpoint reverses a `PAID`/`PREPARING` order (restocks every item, flips to `CANCELLED`), requires the same order-access-token as every other order endpoint, and rejects `PENDING` (use `/cancel`) and `COMPLETED` (already handed over) with a 409. Deliberately backend-only for now — no UI button, since exposing it well is its own design question (the confirmation screen is only up for 3 seconds) not agreed on yet.
  * Verified via curl: kiosk_username persists correctly on created orders; refund correctly restocks (confirmed stock back to original count), rejects a second refund on an already-cancelled order (409), and rejects refunding a still-`PENDING` order (409). Verified the kiosk label renders correctly in the browser (defaults to "kiosk1" with no env configured).

* **Step 18: A small, deliberately non-exhaustive test suite**
  * Scope, by explicit request: prove real testing competence on the pieces of business logic this project actually cares about, not maximum coverage. 11 backend tests, 6 frontend tests.
  * **Planning:** used a Plan subagent to read the actual current source (not assumptions) and turn a rough test list into a concrete, validated one — it caught two real risks worth calling out: (1) tests depending on `seed.py`'s exact product/stock values would silently break if the menu changes later, so `tests/conftest.py` inserts its own small deterministic fixture data instead of importing `PRODUCTS`/`USERS`; (2) `TestClient(app)` used as a context manager (`with TestClient(app) as client:`) runs FastAPI's `lifespan`, which calls `seed.init_db()` against the *real* dev database — so the fixture instantiates it directly instead, skipping lifespan entirely.
  * **Backend** (`backend/tests/`, pytest + `httpx`'s `TestClient`, isolated temp-file SQLite per test via `tmp_path` — not `:memory:`, so the existing WAL-mode pragma listener in `database.py`, registered against the SQLAlchemy `Engine` base class, applies exactly like production): `test_orders.py` covers order creation + the quantity cap, the order-access-token check (wrong token → 404, same as nonexistent — confirms the IDOR fix's disguise behavior; missing header → 422), a successful payment's atomic stock decrement, the insufficient-stock 409/rollback path (two orders racing a stock=1 item), admin-only failure injection (403 for non-admin, 402 + order-stays-PENDING for an admin-forced decline), cancel-only-from-PENDING, and refund-restocks-and-cancels. `test_auth.py` covers login success/failure. `backend/pytest.ini` (`pythonpath = .`) and `backend/requirements-dev.txt` (pytest + httpx, not bundled in the main `requirements.txt`) added alongside.
  * **A genuine bug found via the tests themselves, not just written around:** the first working version of the `client` fixture kept creating the *real* dev `tapngo.db` file even with lifespan skipped — traced it to `services/order_lifecycle.py` importing `SessionLocal` directly from `app.database` instead of going through the `get_db` dependency, combined with a fact that's easy to get wrong: Starlette's `BackgroundTasks` run as part of the *same* request/response cycle, not a detached thread — so a successful `/pay` call was synchronously blocking for the lifecycle timer's real ~8-second sleep *and* bypassing the test DB override to touch the real file. Fixed by monkeypatching `schedule_order_lifecycle` to a no-op in the `client` fixture — the lifecycle timer isn't something this suite needs to exercise anyway. Also dropped total suite runtime from ~12–24s to well under a second.
  * **Frontend** (`frontend/src/**/*.test.ts(x)`, Vitest + `@testing-library/react`, colocated with source): `state/SessionContext.test.tsx` exercises `addToCart`'s quantity cap (`min(MAX_QUANTITY_PER_ITEM, stock)`) via `renderHook` — settles at 5 for a well-stocked item, at 2 for a stock=2 item, and never adds a zero-stock item at all. `lib/api.test.ts` covers `extractErrorMessage` (exported for this purpose — previously private, zero behavior change): a plain string `detail` passes through, a list-of-`{msg}` `detail` (FastAPI's real validation-error shape) gets joined into text instead of stringified into `[object Object]` — a direct regression test for a real bug hit earlier in this project — and a missing/malformed body falls back cleanly. Vitest config lives in the existing `vite.config.ts` (switched its `defineConfig` import to `vitest/config`, which is a superset) rather than a second config file, so the `@` alias and dev proxy don't need duplicating.
  * **Verified the suite isn't vacuous, not just that it passes:** deliberately broke one assertion on each side (backend: an expected stock count; frontend: an expected cart quantity) and confirmed both failed with the correct diff, then reverted.
  * Corrected Step 8 above, which had described (before any test file existed) frontend coverage — idle-timer behavior, single-touch guard, confirmation-screen auto-return — that this suite deliberately doesn't include, since those are UI/integration surfaces disproportionate to the stated scope.

* **Step 19: Containerization**
  * Two decisions settled before writing any files: (1) `VITE_KIOSK_ID` stays a build-time value — Vite bakes env vars into the static bundle at build time regardless, so fighting that for a single-kiosk demo deployment isn't worth it; the `frontend/Dockerfile` exposes it as a build ARG (default `kiosk1`) so the override path exists for a real multi-terminal build, without `docker-compose.yml` needing to configure anything. (2) The SQLite file goes in a named Docker volume (`backend_data`), not the container's own filesystem — otherwise `docker compose down` would silently wipe stock/order history. Both documented in `ARCHITECTURE_DECISIONS.md` section 5.
  * `backend/Dockerfile` — `python:3.12-slim`, installs `requirements.txt`, runs `uvicorn` directly (no extra process manager — a single kiosk backend doesn't need one).
  * `frontend/Dockerfile` — multi-stage: `node:22-alpine` builds the static app (`npm ci && npm run build`), then `nginx:alpine` serves the output. `frontend/nginx.conf` does the routing from section 1: `/` → static files (with `try_files ... /index.html` so React Router's client-side routes like `/menu/drinks` don't 404 on a hard refresh), `/api/` → `http://backend:8000` (Docker Compose's internal DNS resolves the service name).
  * `docker-compose.yml` at the repo root: two services, the backend's port only `expose`d (internal-network-only, reached through the NGINX proxy, not published directly), the frontend on `80:80`.
  * Added `.dockerignore` to both `backend/` and `frontend/` (skip `venv/`/`node_modules/`/test artifacts) to keep build contexts small.
  * **Verification gap, disclosed rather than hidden:** this sandbox has no `docker` group and `sudo` needs a password not available here, so `docker compose up --build` couldn't be run directly to confirm the containers actually build and start. Did what verification was possible without the daemon: `docker compose config` (validates and fully resolves the compose YAML — passed), `npm ci --dry-run` in `frontend/` (confirms `package-lock.json` is in sync, so the Docker build stage's `npm ci` won't fail on a lockfile mismatch), and a manual read of `requirements.txt` (no packages that need compilation on `python:3.12-slim` — all have prebuilt wheels). The user will run the actual `docker compose up --build` and report back.
